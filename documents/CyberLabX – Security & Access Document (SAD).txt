1.  Security  Philosophy  
CyberLabX  is  different  from  a  normal  web  application.  
Students  will  execute  Linux  commands,  network  scans,  and  cybersecurity  tools.  That  means  
security
 
is
 
part
 
of
 
the
 
product
 
itself.
 
Our  security  model  has  four  priorities:  
1.  Protect  student  accounts.  2.  Protect  college  data.  3.  Prevent  students  from  escaping  the  lab  environment.  4.  Prevent  CyberLabX  from  being  used  to  attack  real  systems.  
 
2.  Authentication  Strategy  
Recommended  Authentication  
Email  +  Password  +  JWT  (HttpOnly  Cookies)  
This  is  the  best  balance  between  security  and  implementation  complexity  for  an  educational  
SaaS.
 
Login  Flow  
None
Student   ↓   Email  +  Password   ↓   Backend  verifies  password   ↓   JWT  created   ↓   JWT  stored  in  HttpOnly  Cookie   ↓   Student  is  logged  in  
Why  HttpOnly  Cookies?  
Many  beginner  projects  store  tokens  in  localStorage.  
We  should  not.  
Reasons:  
●  JavaScript  cannot  read  HttpOnly  cookies.  ●  Better  protection  against  XSS.  ●  More  secure  session  handling.  ●  Easier  future  enterprise  deployment.  
 
Password  Policy  
None
None
Minimum:  
●  8  characters  ●  One  uppercase  letter  ●  One  lowercase  letter  ●  One  number  
Recommended:  
●  12+  characters  
Passwords  are  never  stored  directly.  
Only  password  hashes  are  stored.  
 
Password  Storage  
Use  
bcrypt  
or  
Argon2  
Argon2  is  stronger.  
bcrypt  is  perfectly  acceptable  for  Version  1.

15.  Security  Checklist  Before  Launch  
●  HTTPS  enabled.  ●  Secure  cookies  (HttpOnly,  Secure,  SameSite).  ●  Passwords  hashed.  ●  JWT  expiration  configured.  ●  Input  validation  on  every  endpoint.  ●  Role-based  authorization  enforced.  ●  Docker  containers  isolated  and  resource-limited.  ●  Internal-only  lab  network.  ●  Rate  limiting  enabled.  ●  Audit  logging  enabled.  ●  Regular  database  backups.  ●  Secrets  stored  outside  source  code.  ●  Dependency  vulnerability  scanning  completed.  
 
16.  Incident  Response  
If  suspicious  activity  is  detected:  
1.  Record  the  event  in  the  audit  log.  2.  Suspend  the  affected  lab  session.  3.  Preserve  logs  for  investigation.  4.  Notify  the  administrator.  5.  Allow  the  student  to  continue  only  after  the  environment  has  been  reset  if  appropriate.  
The  goal  is  to  protect  the  platform  while  minimizing  disruption  to  legitimate  users.

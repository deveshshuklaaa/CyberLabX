1.  Architecture  Philosophy  
CyberLabX  is  not  just  a  website.  
It  is  composed  of  five  major  systems  working  together:  
                   CyberLabX                    React  Frontend                           │                   REST  API  Gateway                           │                  Express  Backend  API                           │    ┌──────────────┬──────────────┬──────────────┐   │               │               │               │  Auth          Experiment      Lab  Engine     Reports  Service        Service          Service       Service  
                         │                    MongoDB  Database                           │                 Docker  Container  Engine                           │            Kali  +  Target  Machines  Network  
For  Version  1,  these  services  will  exist  as  modules  inside  one  Express  application.  That  keeps  
deployment
 
simple
 
while
 
allowing
 
you
 
to
 
split
 
them
 
into
 
independent
 
services
 
later
 
if
 
needed.

Docker  Architecture  
Docker  Host   │   ├──  MongoDB   ├──  Node   ├──  React   ├──  Nginx   │   └──  Student  Containers         ├──  Student  1         ├──  Student  2  
None
       ├──  Student  3         └──  Student  N  
Each  student  receives  a  fresh,  isolated  container.  
 
Networking  
Student  Browser   ↓   Node  Backend   ↓   Docker  API   ↓   Kali  Container   ↓   Internal  Network   ↓   Target  Machine  
The  container  cannot  reach  the  public  Internet  by  default.  
None
 
Security  
●  JWT  in  HttpOnly  cookies.  ●  Passwords  hashed  with  bcrypt.  ●  Role-Based  Access  Control  (RBAC).  ●  Rate  limiting  on  authentication  endpoints.  ●  Input  validation  using  Zod  or  Joi.  ●  CSRF  protection  if  using  cookies.  ●  Container  resource  limits  (CPU,  memory).  ●  Network  isolation  for  lab  containers.  ●  Audit  logs  for  faculty/admin  actions.

Configuration  Notes  
●  Docker  permissions:  The  backend  will  need  access  to  the  Docker  Engine  to  create  and  
manage
 
lab
 
containers.
 
This
 
is
 
powerful
 
and
 
should
 
be
 
carefully
 
restricted
 
in
 
production.
 ●  Resource  limits:  Configure  CPU  and  memory  limits  for  each  student  container  to  
prevent
 
a
 
single
 
user
 
from
 
exhausting
 
server
 
resources.
 ●  Networking:  Place  lab  containers  on  an  isolated  Docker  network  with  no  outbound  
Internet
 
access
 
unless
 
an
 
experiment
 
explicitly
 
requires
 
it.
 ●  Secrets:  Never  commit  .env files  to  version  control.  Provide  a  .env.example with  
placeholder
 
values.
 ●  Logging:  Centralize  logs  for  the  backend  and  lab  management  to  simplify  
troubleshooting.
 ●  Backups:  Schedule  regular  backups  of  MongoDB  and  generated  reports.
